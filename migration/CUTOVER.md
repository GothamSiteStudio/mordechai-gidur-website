# מעבר מ-Netlify ל-Cloudflare Pages — נוהל ביצוע

נכון ל-30.07.2026. אתר: `mordechaigidur.co.il`

---

## 1. השורה התחתונה מבחינת SEO

**המעבר עצמו לא מקדם ולא מוריד דירוגים.** אותו דומיין, אותן כתובות, אותו HTML —
לגוגל לא משנה מי מארח. אין "בונוס Cloudflare".

מה שכן יכול לעזור, בעקיפין:

| גורם | מצב היום ב-Netlify | אחרי המעבר |
|------|---------------------|-------------|
| נוכחות רשת בישראל | Netlify מגיש דרך AWS Global Accelerator | ל-Cloudflare יש PoP בתל אביב — TTFB נמוך יותר לגולשים ישראלים |
| Cache על נכסים סטטיים | `max-age=0, must-revalidate` על **הכול**, כולל `logo.svg` במשקל 379KB | נפתר ע"י `_headers` — ראו סעיף 2 |
| רוחב פס | מוגבל בתוכנית החינמית | ללא הגבלה |

TTFB הוא קלט ל-LCP, ו-LCP הוא Core Web Vital. אז השיפור אמיתי — אבל הוא
**גורם דירוג חלש**, ורלוונטי רק אם האתר איטי היום. בבדיקה מהמכונה הזו
TTFB יצא 0.86 שניות, אבל זו מדידה מחו"ל ולא מייצגת גולש ישראלי.

**המלצה:** לפני שנוגעים ב-DNS, כדאי למדוד את ה-Core Web Vitals הנוכחיים
בנתוני שדה אמיתיים (PageSpeed Insights / דוח חוויית העמוד ב-Search Console).
אם ה-LCP כבר ירוק — המעבר הוא שיפור תשתית, לא מהלך SEO, ואפשר לעשות אותו
בנחת. הסיכון האמיתי במעבר הוא לא "לא להרוויח" אלא **לשבור ריידיירקטים**,
ולכן סעיף 4 הוא החלק החשוב במסמך הזה.

## 2. מה כבר בוצע (עובד על Netlify כבר עכשיו, ועובר כמו שהוא ל-Cloudflare)

שלושת הדברים האלה לא מחכים למעבר — הם שיפור מיידי:

- **`_headers` חדש בשורש** — תחביר זהה ב-Netlify וב-Cloudflare Pages, לכן
  הקובץ עובד לפני ואחרי בלי שינוי. מגדיר cache אמיתי על CSS/JS/תמונות
  (במקום `max-age=0` על הכול), משאיר HTML ללא cache כדי שעריכות תוכן יעלו
  מיד, ומוסיף `X-Robots-Tag: noindex` על קבצי המקור שנחשפים לציבור
  (`build.py`, `data*.json`, `report.json`, קבצי דוחות ה-SEO).
- **`robots.txt` חדש** — לא היה כזה בכלל. מפנה ל-`sitemap.xml`.
- **מחיקת `privacy.html`** — היה זהה בייט-בייט ל-`privacy-policy.html`,
  ושתי הכתובות `/privacy` ו-`/privacy-policy` החזירו 200. תוכן כפול קלאסי.
  נמחק, ונוסף ריידיירקט `/privacy → /privacy-policy` ב-`_redirects`.

## 3. הקמת הפרויקט ב-Cloudflare (בלי לגעת ב-DNS)

בשלב הזה האתר החי ממשיך לרוץ על Netlify. שום דבר לא מסוכן.

1. Cloudflare Dashboard → **Workers & Pages** → Create → **Pages** →
   Connect to Git → לבחור `GothamSiteStudio/mordechai-gidur-website`, ענף `main`.
2. הגדרות ה-build — האתר בנוי מראש וה-HTML מקומיט לגיט, אז אין מה לבנות:

   | שדה | ערך |
   |------|------|
   | Framework preset | **None** |
   | Build command | **להשאיר ריק** |
   | Build output directory | `/` |
   | Root directory | `/` |

3. Save and Deploy. מתקבלת כתובת תצוגה מסוג `https://<project>.pages.dev`.

## 4. אימות לפני החלפת DNS ← אל תדלגו על זה

זה הסעיף שמונע נפילת דירוגים. ב-`_redirects` יש 43 ריידיירקטים של 301
שגוגל כבר עיכל, וכל אחד מהם חייב לשרוד את המעבר.

יש הבדל תחבירי אמיתי בין הפלטפורמות:

- **Netlify** דורש `301!` — סימן הקריאה כופה ריידיירקט גם כשקיים קובץ
  באותו נתיב. בלעדיו Netlify יגיש את הקובץ במקום להפנות.
- **Cloudflare Pages** לא מכיר את הדגל `!` בכלל. מצד שני הוא מבצע את
  ההפניה `/foo.html → /foo` ו-`/dir/index.html → /dir/` **באופן מובנה**,
  כך ש-40 מתוך 43 השורות מיותרות שם.

לכן `migration/_redirects` מכיל רק את הכלל שקלאודפלייר לא יכול להסיק לבד
(`/privacy`). **הקובץ הזה נשאר ב-`migration/` עד הרגע האחרון** — אסור לשים
אותו בשורש כל עוד האתר על Netlify, כי הסרת ה-`!` תשבור את הריידיירקטים החיים.

להריץ מול כתובת התצוגה:

```bash
python migration/verify_redirects.py https://YOUR-PROJECT.pages.dev
```

הסקריפט בודק 83 נתיבים — כל הכתובות הקנוניות מ-`sitemap.xml` וכל נתיבי
ה-`.html` הישנים — ומשווה סטטוס ויעד הפניה מול האתר החי. פלט תקין מסתיים ב-
`All 83 paths match production. Safe to flip DNS.` כל `DIFF` הוא עצירה:
לתקן, לפרוס מחדש, להריץ שוב.

## 5. החלפת ה-DNS

היום הדומיין יושב על שרתי שמות של הרשם הישראלי (`park1/park2.livedns.co.il`).
**כדי לחבר את הדומיין הראשי (apex) ל-Cloudflare Pages חייבים להעביר את
שרתי השמות ל-Cloudflare** — apex לא יכול להיות CNAME אצל רוב הרשמים.

בדקתי את הרשומות הקיימות. המצב נוח:

| רשומה | ערך נוכחי | מה לעשות |
|--------|-----------|-----------|
| `A @` | `75.2.60.5` (Netlify) | Cloudflare ייצור אותה אוטומטית מול Pages |
| `CNAME www` | `mordechaigidur.netlify.app` | להפנות ל-Pages |
| `TXT @` | `google-site-verification=Md_-kl-ct4RQEtOUnltUJAr_0_SuxT7jogHZOJLMz3E` | ⚠️ **חובה להעתיק** |
| `MX` | **אין** | אין דוא"ל על הדומיין — הסיכון הגדול במעברי DNS לא קיים כאן |

⚠️ רשומת ה-TXT היא מה שמאמת את נכס ה-Search Console
(`sc-domain:mordechaigidur.co.il`). אם היא לא תעבור — האימות נשבר ומאבדים
גישה לנתונים. לוודא שהיא קיימת בקלאודפלייר **לפני** שמחליפים שרתי שמות.

סדר הפעולות:

1. Cloudflare → Add a site → `mordechaigidur.co.il` → תוכנית Free.
2. לעבור על הרשומות שקלאודפלייר סרק אוטומטית ולהשלים ידנית כל מה שחסר,
   בעיקר ה-TXT של גוגל.
3. אצל הרשם (livedns) להחליף את שרתי השמות לשניים שקלאודפלייר נותן.
4. להמתין להתפשטות — בדרך כלל דקות עד שעות. ה-TTL הנוכחי הוא 4 שעות.
5. ב-Pages → Custom domains → להוסיף `mordechaigidur.co.il` ו-`www`.
   לוודא ש-`www` מפנה 301 לדומיין ללא www, כמו היום.
6. להריץ שוב, הפעם מול הדומיין האמיתי:
   ```bash
   python migration/verify_redirects.py https://mordechaigidur.co.il
   ```

## 6. אחרי המעבר

- להעביר את `migration/_redirects` לשורש (להחליף את גרסת Netlify),
  ולמחוק את תיקיית `migration/`.
- לוודא HTTPS תקין ושאין תקופת ביניים בלי תעודה.
- Search Console → Sitemaps → להגיש מחדש את `sitemap.xml`.
  (ה-MCP כאן במצב קריאה בלבד — חייב להיעשות ידנית בממשק.)
- לעקוב שבועיים אחרי דוח הכיסוי ואחרי קליקים/הופעות. תנודה קלה בימים
  הראשונים היא נורמלית; ירידה מתמשכת מעידה על ריידיירקט שבור.
- לבטל את פרויקט ה-Netlify רק אחרי שבועיים־שלושה יציבים.

## 8. דברים שצפו במהלך הבדיקה ולא קשורים למעבר

- `logo.svg` שוקל **379KB**. זה SVG, לא תמונה — כנראה מכיל נתיבים מיוצאים
  מ-Illustrator. אופטימיזציה (SVGO) תוריד אותו לעשירית. משפיע על LCP הרבה
  יותר מכל החלפת אחסון.
- `report.json` במשקל 496KB ו-`data.json` במשקל 113KB מוגשים לציבור.
  ה-`noindex` שהוספתי מונע אינדוקס, אבל עדיף פשוט לא לפרוס אותם.
- קבצי `SEO-Report-2026-06.md` ו-`SEO-site-health-report-2026-07-12.md`
  נגישים לכל מי שמנחש את הכתובת — כולל מתחרים. שווה להוציא מהפריסה.
